# Architecture Load Simulator — Механика игры

## Обзор

Симулятор веб-архитектуры с экономической петлёй. Игрок размещает узлы (Source → Backend → PostgreSQL) на canvas, соединяет их, и наблюдает как запросы-частицы текут по графу. Успешные запросы приносят прогресс к новым пользователям, ошибки снижают satisfaction и вызывают churn.

---

## 1. Узлы архитектуры

### TrafficSource
- **Роль:** генерирует API-запросы (жёлтые частицы)
- **Порты:** нет входов, 1 выход `api`
- **autoRate** — запросов/сек, вычисляется симуляцией как `users × 0.1 × randomFactor(0.7–1.3)`
- **Ручной спавн:** кнопка «⚡ Generate Request» вызывает `generateFromSources()` — создаёт один API-запрос вручную, не зависит от autoRate
- **Accumulator-паттерн:** авто-спавн синхронизирован с `requestAnimationFrame`, никаких `setInterval`. При 0 пользователей autoRate = 0, запросы только вручную

### Backend
- **Роль:** конвертор: 1 API-запрос → N SQL-запросов (синие частицы). Wait-all семантика: родитель ждёт всех детей
- **Порты:** 1 вход `api`, 1 выход `sql`
- **Режимы:** Sequential (дети отправляются по одному, ошибка ребёнка = немедленный фейл родителя) или Parallel (все сразу, ждём всех)
- **N (количество детей):** настраиваемый диапазон, по умолчанию 1–5
- **Processing time база:** случайное значение из диапазона (300–1500ms), назначается на Backend для каждого SQL-запроса
- **Timeout:** настраиваемый (500–30000ms). По истечению: abort (убить детей) или detach (дать детям доработать)
- **Индикатор:** subtitle `pending: N` над узлом

### PostgreSQL
- **Роль:** обрабатывает SQL-запросы. Терминальный узел
- **Порты:** 1 вход `sql`, нет выходов
- **Tier'ы:** XS (5 conn), S (20), M (60), L (120), XL (250). Сейчас активен только XS
- **Capacity:** при `activeConnections >= maxConnections` → DROP (частица сразу красная, ошибка)
- **Processing time:** `baseProcessingTime + ⌊dbSize / 100⌋ × 100ms`
- **dbSize:** растёт с каждым успешным запросом → время обработки увеличивается со временем
- **Индикатор:** subtitle `3/5 conn · DB: 42`, фон краснеет при перегрузке

## 2. Частицы (Particle)

State machine:
```
traveling → pending   (Backend — ждёт детей, жёлтая пульсация)
         → processing (PostgreSQL — синяя пульсация + кольцо прогресса)
         → success    (зелёная вспышка-кольцо, 400ms)
         → error      (красная вспышка-кольцо, 400ms)
```

- **Скорость полёта:** 0.75 progress/сек (PARTICLE_SPEED)
- **Визуальные эффекты:** пульсация, свечение (shadowBlur), прогресс-кольцо при processing, разлёт parked-частиц по окружности вокруг узла
- **serviceMs:** накапливается только во время processing. Дети передают своё время родителю при завершении

## 3. Экономическая петля

### Пользователи (users)
- **Старт:** 0
- **Рост:** через прогресс-бар
- **Прогресс-бар:** `userProgress (текущий) / userProgressTarget (порог)`
  - Каждый **успешный API-запрос** (родитель завершился, все дети успешны) → **+5** прогресса
  - При `userProgress ≥ userProgressTarget`:
    - `users += 1`
    - `userProgress -= userProgressTarget`
    - `userProgressTarget = 5 + users × 2` (растёт линейно: 5, 7, 9, 11…)
    - `satisfaction += 3` (буст от роста)
- **Генерация RPS:** `autoRate = users × 0.1 × randomFactor(0.7–1.3)`. Шум обновляется медленно (~0.5% шанс на тик), чтобы трафик не дёргался
- **Тестовый слайдер:** «Test users» (0–200) задаёт users напрямую, обходя прогресс

### Satisfaction (0–100%)
- **Старт:** 100% (чистая репутация)
- **Рост:** `+0.05%` за каждый успех (SQL + API)
- **Падение:** `−0.5%` за каждую ошибку (SQL + API)
- **Decay:** `−0.02%/сек` — естественное затухание без активности
- **Визуализация:** цвет в статистике: зелёный > 60%, жёлтый 30–60%, красный < 30%

### Churn (отток пользователей)
- **Активируется** когда satisfaction < 30
- **Скорость:** `churnRate = (30 − satisfaction) / 30 × 0.5` юзеров/сек
  - При 0% satisfaction: 0.5 юзеров/сек
  - При 20%: ~0.17 юзеров/сек
- **Целочисленный:** дробная часть копится в `_churnAccumulator`, юзеры теряются по одному
- **Сброс:** при восстановлении satisfaction > 30 аккумулятор обнуляется

## 4. Игровой цикл (per-tick)

Каждый кадр (~60Hz) в `Simulation.update(dt, simTime)`:

1. **Снапшот** счётчиков success/error до тика
2. **Движение** travelling-частиц вдоль connections
3. **Прибытие** → вызов `node.receive(particle, sim)` — меняет state частицы
4. **Тики узлов:** TrafficSource (accumulator-спавн), Backend (timeout-проверка), PostgreSQL (завершение processing)
5. **Очистка** success/error-частиц после 400ms вспышки
6. **Экономика:**
   - Δsuccess → +прогресс
   - Проверка milestone → +юзер
   - Δsuccess/Δerror → ±satisfaction
   - Satisfaction < 30 → churn
   - users → autoRate на все TrafficSource

## 7. Динамика игры

1. **Старт:** 0 юзеров, satisfaction 100%. Игрок жмёт Generate → API-запросы идут вручную
2. **Первые юзеры:** успешные API-запросы дают прогресс → появляются юзеры → начинается автотрафик
3. **Рост:** больше юзеров → больше RPS → больше успехов → больше прогресса → ещё больше юзеров
4. **Capacity wall:** PostgreSQL XS (5 соединений) перестаёт справляться → дропы → satisfaction падает
5. **Кризис:** satisfaction < 30 → начинается churn → юзеры уходят → RPS падает → меньше ошибок → satisfaction может восстановиться
6. **Равновесие:** система самобалансируется на уровне, который архитектура способна обслужить. Чтобы расти дальше — нужно улучшать инфраструктуру (будущий этап)
